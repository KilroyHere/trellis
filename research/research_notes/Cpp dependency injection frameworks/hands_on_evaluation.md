# Hands-on evaluation of C++ DI frameworks with GCC 13.3 and Clang 18.1

Scope: first-hand experiments run on 2026-10-30 in a Linux container (Ubuntu 24.04, KVM guest, 4 vCPUs "Intel(R) Xeon(R) Processor @ 2.10GHz", 15 GiB RAM; `g++ (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0`; `Ubuntu clang version 18.1.3 (1ubuntu1)` using libstdc++ 13; CMake 3.28.3; Boost 1.83 headers from apt; Python 3.13). All code is in `/home/user/cpp-di-research/experiments/` (rerun with `scripts/run.sh <deps> <build> <results>`, see [experiments/README.md](../../experiments/README.md)); raw data in [experiments/results/results.json](../../experiments/results/results.json), tables in [experiments/results/summary.md](../../experiments/results/summary.md), compiler/runtime outputs in `experiments/results/logs/`. Unless stated otherwise: `-O2 -Wall -Wextra`, one translation unit, compile-only wall time = median of 5 runs after 1 warm-up. The container restarted during the scaling phase. Scaling for N≤25 was recovered from the log, and N=50/100 were measured afterwards under time and memory caps (section 4). The scripts' optional `multitu` (Fruit split across translation units) and `extras` (Boost-only and Fruit-sources compile checks) phases were not run.

## 1. Equivalent programs: the scenario and where frameworks forced deviations

### Takeaway
One shared, macro-free domain (`ILogger`/`IRepository`/`IClock`, a `Config` instance, `Service`, `App`, shared and unique lifetimes) could be wired idiomatically by Boost.DI, dingo, Kangaru and qlibs/di. Fruit and Hypodermic needed hand-written factory lambdas because they cannot inject `std::unique_ptr` parameters, and Boost.DI's default `singleton` is process-wide rather than per-injector. All seven programs pass the same runtime wiring check.

### Cited Findings
- Scenario (identical classes in all programs): `ILogger -> CountingLogger` and `IRepository -> InMemoryRepository` shared; `IClock -> SteadyClock` unique per resolution; `Config` bound as an instance by reference; `Service(shared_ptr<ILogger>, shared_ptr<IRepository>, unique_ptr<IClock>, const Config&)`; `App(unique_ptr<Service>, shared_ptr<ILogger>)` resolved twice — [experiments/common/domain.hpp](../../experiments/common/domain.hpp)
- Every program verifies the semantics at run time (same logger/repository across both Apps, different Service/clock, Config is the caller's object) and printed `wiring_errors=0 handled=6 log_lines=8 repo_size=6` for every compiler/standard that compiled — [experiments/results/summary.md](../../experiments/results/summary.md)
- Boost.DI 1.3.2's core `di::singleton` scope keeps the object in a function-local `static` (`static std::shared_ptr<T_> object{provider.get()};`), i.e. one instance per process and binding, not per injector — [boost-ext/di di.hpp L1897](https://github.com/boost-ext/di/blob/20b6454c889f23c1e7c9eb5136cd7e3d6f6d718d/include/boost/di.hpp#L1897) (also L1877); the per-injector alternative is the extension scope `di::extension::shared` — [boost-ext/di extension/scopes/shared.hpp](https://github.com/boost-ext/di/blob/20b6454c889f23c1e7c9eb5136cd7e3d6f6d718d/extension/include/boost/di/extension/scopes/shared.hpp)
- Boost.DI constructor deduction is limited to 10 parameters by default (`BOOST_DI_CFG_CTOR_LIMIT_SIZE 10`) — [boost-ext/di di.hpp L953](https://github.com/boost-ext/di/blob/20b6454c889f23c1e7c9eb5136cd7e3d6f6d718d/include/boost/di.hpp#L953)
- Fruit's documented injectable parameter types for `registerConstructor` are `C, C*, C&, const C*, const C&, shared_ptr<C>, Provider<C>` (and annotated forms) — no `unique_ptr<C>`; non-singleton objects are obtained as `std::function<std::unique_ptr<I>(...)>` factories — [google/fruit component.h L310-L327](https://github.com/google/fruit/blob/8149131119475ccaae3c1ae386fe9f2c679317f0/include/fruit/component.h#L310) and the `bind()` docs above it ([L190-L250](https://github.com/google/fruit/blob/8149131119475ccaae3c1ae386fe9f2c679317f0/include/fruit/component.h#L190)); "Registering stateful functors (including lambdas with captures) is NOT supported" — [component.h L787](https://github.com/google/fruit/blob/8149131119475ccaae3c1ae386fe9f2c679317f0/include/fruit/component.h#L787)
- Consequently the Fruit program registers leaf types with `registerConstructor<>()`, binds `IClock` through a `registerFactory<std::unique_ptr<SteadyClock>()>`, and builds `Service`/`App` in `registerFactory` lambdas; the root is a `std::function<std::unique_ptr<App>()>`; Fruit's `shared_ptr<ILogger>` is non-owning (injector must outlive the Apps) — [experiments/fruit/main.cpp](../../experiments/fruit/main.cpp)
- Hypodermic auto-wires only constructor arguments of type `std::shared_ptr<T>`, `std::vector<std::shared_ptr<T>>`, `std::function<std::shared_ptr<T>()>` and its `FactoryWrapper<T>` — [Hypodermic IsSupportedArgument.h L20-L50](https://github.com/ybainier/Hypodermic/blob/0e0d85d70aa2f2391dfd84f8af4a3863d4fb1611/Hypodermic/IsSupportedArgument.h#L20); so `App` is registered with `registerInstanceFactory` and the lambda builds `Service` and the clock by hand, resolving only `ILogger`, `IRepository` and `Config` from the container — [experiments/hypodermic/main.cpp](../../experiments/hypodermic/main.cpp)
- Kangaru needs an explicit service-definition struct per type with a `kgr::dependency<...>` list; interfaces are bound with `abstract_shared_service` + `overrides`/`defaults_to`, which applies to single (shared) services, so the unique clock is defined on `SteadyClock` itself and converts to `unique_ptr<IClock>` — [experiments/kangaru/main.cpp](../../experiments/kangaru/main.cpp); Kangaru docs on abstract/default services — [kangaru doc/section03_polymorphic.md](https://github.com/gracicot/kangaru/blob/ab498eb9db0de74ffebc46f395b9a31093017412/doc/section03_polymorphic.md)
- dingo resolves only registered types (so `Service` and `App` are registered too) and fixes the interface at registration with `interfaces<...>` — [experiments/dingo/main.cpp](../../experiments/dingo/main.cpp); [dingo docs/core-concepts.md](https://github.com/romanpauk/dingo/blob/ccafcb6cbde54fb2819a3da8243106642f3b1711/docs/core-concepts.md)
- qlibs/di is a building block rather than a container: `di::make<T>(overload{...})` deduces constructor parameters and picks the most constrained lambda for each; the README's "DIY" injector implements singletons with a function-local `static` — [qlibs/di `di` L296-L341](https://github.com/qlibs/di/blob/bdafce9baa19dfc503d6acd5f5abf91f503fa5ef/di#L296). The program keeps shared objects in a per-container `Scope` struct captured by reference instead — [experiments/qlibs_di/main.cpp](../../experiments/qlibs_di/main.cpp)
- qlibs/di's `ctor_traits<std::unique_ptr<T>>::operator()` is declared to return `std::shared_ptr<T>` (it wraps `std::make_unique`), so the generic path cannot satisfy a `std::unique_ptr` parameter and explicit `unique_ptr` bindings were written — [qlibs/di `di` L756-L764](https://github.com/qlibs/di/blob/bdafce9baa19dfc503d6acd5f5abf91f503fa5ef/di#L756)

### Inferences
- The frameworks split into "type-driven" ones whose idiom matches modern smart-pointer constructors (Boost.DI, dingo, qlibs/di, Kangaru with definitions) and ones with a narrower ownership model (Fruit: injector-owned singletons + factories; Hypodermic: `shared_ptr` everywhere). A codebase built around `unique_ptr` ownership will need adapter code with the latter two.
- The qlibs/di `unique_ptr` path returning `shared_ptr` looks like a bug (inferred from reading the header; not reported upstream as far as checked here).
- Because Boost.DI's default singleton is process-global, "create a new injector" does not reset shared state; tests that build many injectors should use `extension::shared` or another scope.

### Gaps
- Programs were written by one person from the libraries' docs/headers; a framework expert might find a more idiomatic (e.g. INJECT-annotated) Fruit or a shared_ptr-only Hypodermic design. Those variants were not measured for the small scenario (the generated scaling graph does use shared_ptr-only constructors, which suit Hypodermic and Fruit).
- Kangaru 5 (branch `dev-5.x.y`) and the default-branch heads of the other projects were not tested; only the latest release tags.

## 2. Does each framework compile cleanly (GCC 13.3 / Clang 18.1, C++17 / C++20, -Wall -Wextra)?

### Takeaway
All frameworks compiled and ran correctly in both modes with both compilers, except qlibs/di, which is C++20-only by design. Under `-Wall -Wextra`, only Kangaru produced warnings in its own headers: one `-Wunused-variable` per shared service, a dead variable at `container.hpp:443`. Fruit's library is always built as C++11 because its CMake script hard-codes `-std=c++11`.

### Cited Findings
- Compile matrix result: manual, Boost.DI, Fruit, Kangaru, dingo, Hypodermic compile with g++ and clang++ in `-std=c++17` and `-std=c++20`; qlibs/di compiles only in C++20 — [experiments/results/summary.md](../../experiments/results/summary.md) (compile matrix table)
- qlibs/di in C++17 fails at the first concept: GCC `di:705:28: error: 'concept' does not name a type; did you mean 'const'?` (1,176 lines / 111,230 bytes of output), Clang `di:705:28: error: unknown type name 'concept'` (68 lines / 6,791 bytes) — [experiments/results/logs/compile/](../../experiments/results/logs/compile/) (`qlibs_di-gcc-c++17.txt`, `qlibs_di-clang-c++17.txt`); its README states the requirement "C++20 (clang++13+, g++11+)" — [qlibs/di `di` L52](https://github.com/qlibs/di/blob/bdafce9baa19dfc503d6acd5f5abf91f503fa5ef/di#L52)
- Warnings with `-Wall -Wextra`: 0 for manual, Boost.DI, Fruit, dingo, Hypodermic and qlibs/di in every configuration; Kangaru 3 per configuration, all `kangaru/container.hpp:443: warning: unused variable 'service' [-Wunused-variable]` (one per single service instantiated: Config, logger, repository). Each comes with a template-instantiation backtrace: 38 lines / 17,644 bytes of output with GCC, 97 lines / 13,167 bytes with Clang — [experiments/results/summary.md](../../experiments/results/summary.md), [experiments/results/logs/compile/kangaru-gcc-c++20.txt](../../experiments/results/logs/compile/kangaru-gcc-c++20.txt)
- The warned line `auto& service = static_unwrap_single<T>(storage);` is never used afterwards (same pattern also at line 317) — [kangaru container.hpp L443](https://github.com/gracicot/kangaru/blob/ab498eb9db0de74ffebc46f395b9a31093017412/include/kangaru/container.hpp#L443)
- Warning-free results partly reflect how headers are seen: qlibs/di marks its header `#pragma GCC system_header`, which suppresses its warnings — [qlibs/di `di` L690](https://github.com/qlibs/di/blob/bdafce9baa19dfc503d6acd5f5abf91f503fa5ef/di#L690); Boost headers used by Hypodermic come from `/usr/include` (system headers). All framework headers were passed with `-I` (not `-isystem`) — command lines in [experiments/results/results.json](../../experiments/results/results.json)
- Fruit's library (10 sources) built with zero warnings under its own `-W -Wall` for gcc/clang x 17/20, but the compile line is `... -std=gnu++20 -std=c++11 -W -Wall ...` because the top-level CMakeLists appends `-std=c++11` — [google/fruit CMakeLists.txt L48](https://github.com/google/fruit/blob/8149131119475ccaae3c1ae386fe9f2c679317f0/CMakeLists.txt#L48); the resulting `libfruit.a` is byte-identical in size for the 17 and 20 builds (381,892 bytes GCC, 301,994 bytes Clang) — build logs under the build directory, procedure in [experiments/scripts/prepare_deps.sh](../../experiments/scripts/prepare_deps.sh)
- dingo's README lists "Tested with: C++17, C++20, C++23, C++26; GCC 12-14; Clang 17-19" — [dingo README](https://github.com/romanpauk/dingo/blob/ccafcb6cbde54fb2819a3da8243106642f3b1711/README.md), consistent with the clean results here.

### Inferences
- For `-Werror` builds, Kangaru 4.3.2 needs `-Wno-unused-variable` or `-isystem` includes; the other five are clean at this warning level (with the system-header caveat for qlibs/di).
- The qlibs/di C++17 failure is an expected requirements mismatch, not a bug; it shows how verbose GCC gets when a concepts-based header is parsed in the wrong mode (110 KB of errors).

### Gaps
- Not tested: `-Wpedantic`, `-Wshadow`, `-Wconversion`, `-Weffc++`, sanitizers, MSVC, C++23/26 modes, libc++ (Clang used libstdc++ 13).
- Fruit's own library sources were only compiled through Fruit's CMake, i.e. as C++11. A direct C++17/C++20 `-Wall -Wextra` compile of them is implemented (the `extras` phase in `measure.py`) but was not run before the container restart.
- Boost.DI's default branch has a commit "fix error with clang 21" after v1.3.2 (section 7), so v1.3.2 may not build with Clang 21; only Clang 18.1.3 was tested here.

## 3. Compile time, compiler memory and binary size (small scenario)

### Takeaway
Measured against the manual baseline compiled the same way, qlibs/di adds almost nothing (+0.01 s GCC, +0.09 s Clang in C++20) and Boost.DI adds 0.23–0.37 s. Fruit and Kangaru add about 0.9–1.4 s, dingo about 2.4 s, and Hypodermic 6.7–8.0 s, probably mostly from the Boost headers it includes (inferred from the preprocessed size; not timed separately). Stripped binaries follow the same order: qlibs/di and Boost.DI are within 0–8 KB (1–2 pages of 4 KiB) of manual at 15–23 KB, Kangaru is ~35 KB, dingo 113–121 KB, Fruit 134–146 KB including the static `libfruit.a`, and Hypodermic 318–327 KB.

### Cited Findings
- Compile-only wall time, median of 5 (s), [GCC C++17 / GCC C++20 / Clang C++17 / Clang C++20]: manual 0.49 / 1.20 / 0.49 / 1.41; Boost.DI 0.74 / 1.47 / 0.86 / 1.64; Fruit 1.44 / 2.20 / 1.57 / 2.43; Kangaru 1.39 / 2.06 / 1.91 / 2.71; dingo 2.97 / 3.54 / 2.87 / 3.80; Hypodermic 8.25 / 9.23 / 7.66 / 8.13; qlibs/di – / 1.21 / – / 1.50 (min–max spreads within about ±10 %) — [experiments/results/summary.md](../../experiments/results/summary.md)
- Same table, peak compiler RSS (MB, GCC C++20 / Clang C++20): manual 164 / 152; Boost.DI 206 / 171; Fruit 265 / 207; Kangaru 249 / 190; dingo 305 / 215; Hypodermic 522 / 354; qlibs/di 180 / 164 — [experiments/results/summary.md](../../experiments/results/summary.md)
- Preprocessed translation-unit size (`-E -P` lines, GCC C++17 / C++20): manual 28,924 / 64,923; Boost.DI 51,420 / 82,893; Fruit 48,033 / 81,331; Kangaru 48,515 / 76,699; dingo 53,248 / 85,246; Hypodermic 115,854 / 139,137; qlibs/di – / 65,194 — [experiments/results/results.json](../../experiments/results/results.json) (`preprocessed_lines`)
- Stripped binary size (bytes, GCC C++17 / GCC C++20 / Clang C++17 / Clang C++20): manual 22,832 / 18,736 / 14,744 / 14,744; Boost.DI 22,832 / 22,832 / 22,992 / 22,992; Fruit 145,712 / 145,712 / 133,800 / 133,800 (includes static `libfruit.a`); Kangaru 35,120 / 35,120 / 35,304 / 35,304; dingo 117,112 / 117,112 / 113,224 / 121,416; Hypodermic 317,792 / 317,792 / 326,536 / 326,520; qlibs/di – / 18,736 / – / 18,840 — [experiments/results/summary.md](../../experiments/results/summary.md)

- Hypodermic's own headers total 4,854 lines, yet its preprocessed C++20 translation unit is 74,214 lines larger than the manual one (139,137 against 64,923 with GCC). The extra code therefore comes overwhelmingly from the headers it includes: `boost/signals2.hpp`, `boost/algorithm/string.hpp`, Boost.Range, and whatever they pull in — [experiments/results/results.json](../../experiments/results/results.json) (`preprocessed_lines`), [Hypodermic headers](https://github.com/ybainier/Hypodermic/tree/0e0d85d70aa2f2391dfd84f8af4a3863d4fb1611/Hypodermic)
- Fruit's library build (configure + build of 10 sources, `-j4`) took 4.3–5.9 s per compiler/standard; it is not included in the per-TU numbers above — [experiments/scripts/prepare_deps.sh](../../experiments/scripts/prepare_deps.sh) (prints the time; first run on 2026-10-30: 4.73 s gcc-17, 4.31 s gcc-20, 5.88 s clang-17, 5.48 s clang-20)
- Published comparison points (older compilers, different scenarios): Boost.DI's own benchmark page reports, for "create a unique objects tree" with 64 types and 0 bindings on Clang 3.7, compile times of 0.063 s (baseline) / 0.376 s (Boost.DI) / 2.329 s (Fruit) and executable sizes of 4.2K / 8.5K / 213K — [boost-ext/di doc/benchmarks.md](https://github.com/boost-ext/di/blob/20b6454c889f23c1e7c9eb5136cd7e3d6f6d718d/doc/benchmarks.md); Fruit's wiki (last edited May 2020, Clang 10 / GCC 9) reports stripped executables of 390 KB (Fruit) vs 576–761 KB (Boost.DI) vs 30–34 KB (simple DI) for 100 classes — [Fruit wiki: Benchmarks](https://github.com/google/fruit/wiki/benchmarks)

### Inferences
- In C++20 mode the standard library alone more than doubles the baseline cost (manual: 0.49 s → 1.20–1.41 s, 28.9k → 64.9k preprocessed lines), so a framework's own cost is best read as the delta over manual in the same mode.
- qlibs/di and Boost.DI compile down to essentially the manual code (same or near-same binary size), consistent with their compile-time-only design; the runtime containers (dingo, Hypodermic) and Fruit pay for type-erased runtime machinery in both binary size and compile time.
- For a small program the absolute differences (≤1.5 s, except Hypodermic) are unlikely to matter; the scaling section is more decision-relevant.
- Hypodermic's high fixed compile cost (about 7–8 s even for this tiny program) is most likely the price of its Boost dependency rather than of its own 4.9k lines of headers, so it is paid by every translation unit that includes `Hypodermic.h`.

### Gaps
- Single-TU, single-scenario measurements; no measurement of incremental rebuilds, precompiled headers, or modules (qlibs/di ships a `di.cppm` module file that was not tested).
- Binary size is quantised by 4 KiB segment alignment in the stripped files; see the `.text` sizes for finer comparison.
- How much of Hypodermic's compile time is Boost was not timed directly; the `extras` phase that compiles a TU with only those Boost headers was not run.

## 4. Scaling: compile time for generated graphs of 10–100 components

### Takeaway
With 100 interface/implementation pairs in one translation unit (C++20 `-O2`, GCC / Clang), Boost.DI costs barely more than hand-wiring: 6.8 / 6.3 s against 5.5 / 4.2 s. Fruit with one component function per class takes 18.1 / 16.3 s, Kangaru 22.5 / 21.6 s, dingo 26.9 / 27.7 s and Hypodermic 75.0 / 54.9 s. Growth from N=50 to N=100 is close to linear for all of them (×1.8–2.2), and peak compiler memory stays at or below 1.2 GB except for Hypodermic (2.6 GB with GCC). Two set-ups blow up. A single flat Fruit component was OOM-killed at about 13.9 GB at N=25 with both compilers. qlibs/di went from 2.75 s at N=10 to 518 s and 10.8 GB at N=25 with GCC.

### Cited Findings
- Graph and method: a deterministic DAG of N interface/implementation pairs; each implementation's constructor takes 1–3 `std::shared_ptr<I_d>` (always component k-1 plus up to two earlier ones), every component is shared, and `Root` depends on the last one. The class code is identical for all frameworks; only the wiring differs. Fruit is generated two ways: one component function per class installing its dependencies' components (`fruit`), and all bindings chained in one component (`fruit_flat`). Each binary prints a checksum that is compared with the manual wiring's, and every binary that compiled matched. Compiles are compile-only (`-c`), median of 3 runs (1 run if a compile exceeded 60 s; Hypodermic at N≥50 was run once) — [experiments/scripts/gen_scaling.py](../../experiments/scripts/gen_scaling.py), [experiments/scripts/measure.py](../../experiments/scripts/measure.py), [experiments/results/summary.md](../../experiments/results/summary.md) (scaling table)
- Compile time in seconds (GCC / Clang) for N = 10 → 25 → 50 → 100 — [experiments/results/summary.md](../../experiments/results/summary.md), raw records in [experiments/results/results.json](../../experiments/results/results.json):
  - manual: 1.06/0.90 → 2.13/1.64 → 2.51/2.18 → 5.51/4.23
  - Boost.DI: 1.40/1.33 → 2.66/2.38 → 3.72/3.29 → 6.84/6.30
  - Fruit, one component per class: 2.46/2.59 → 4.85/5.85 → 9.47/8.09 → 18.06/16.25
  - Kangaru: 3.27/3.58 → 7.39/7.69 → 11.02/10.48 → 22.50/21.64
  - dingo: 4.62/4.92 → 9.71/9.64 → 14.13/14.08 → 26.85/27.72
  - Hypodermic: 13.46/12.29 → 23.99/21.03 → 36.97/29.01 → 74.97/54.89
  - Fruit, flat single component: 4.02/5.55 → OOM-killed with both compilers → not run at N≥50
  - qlibs/di: 2.75/6.58 → 518.08 s with GCC / unfinished with Clang (see below) → not run at N≥50
- Marginal cost per extra component, from the N=50 and N=100 points (GCC / Clang, seconds): manual 0.060 / 0.041; Boost.DI 0.062 / 0.060; Fruit 0.172 / 0.163; Kangaru 0.230 / 0.223; dingo 0.254 / 0.273; Hypodermic 0.760 / 0.518. These are computed from the medians above — [experiments/results/summary.md](../../experiments/results/summary.md)
- Peak compiler RSS at N=100 (GCC / Clang): manual 363 / 232 MB; Boost.DI 487 / 341 MB; Fruit 1,071 / 1,039 MB; Kangaru 1,145 / 709 MB; dingo 1,200 / 840 MB; Hypodermic 2,626 / 1,197 MB — [experiments/results/summary.md](../../experiments/results/summary.md)
- Stripped binary size at N=100 (GCC / Clang, bytes): manual 264,496 / 289,152; Boost.DI 313,648 / 346,552; Fruit 551,216 / 551,576; Kangaru 657,712 / 911,816; dingo 1,411,448 / 1,722,936; Hypodermic 4,733,280 / 4,766,576 — [experiments/results/summary.md](../../experiments/results/summary.md)
- Flat Fruit component: at N=10 it already needed 486 / 471 MB and 4.0 / 5.6 s, against 280 / 231 MB and 2.5 / 2.6 s for the per-class version. At N=25 (about 50 chained `registerConstructor`/`bind` calls) the kernel log shows `Memory cgroup out of memory: Killed process ... (cc1plus) ... anon-rss:13938296kB` and the same for `clang++` at `anon-rss:13936784kB` — [experiments/results/logs/scaling/oom_kills_dmesg.txt](../../experiments/results/logs/scaling/oom_kills_dmesg.txt), [experiments/results/summary.md](../../experiments/results/summary.md)
- qlibs/di: N=25 with GCC took 518.08 s and 10,807 MB peak RSS, producing a correct binary, against 2.75 s and 230 MB at N=10. With Clang it was already 6.58 s at N=10. The N=25 Clang compile was still running, at about 5.1 GB RSS after 102 s (seen with `ps`), when the container restarted, so it has no result — [experiments/results/summary.md](../../experiments/results/summary.md), [experiments/README.md](../../experiments/README.md) (notes on the run)
- In qlibs/di every nested resolution wraps the overload set in a `provider<T, Index, TParent>` that inherits from its parent provider, so a dependency reached through a longer path is a different type; `make()` builds a new provider per constructor parameter at every level — [qlibs/di `di` L790-L849](https://github.com/qlibs/di/blob/bdafce9baa19dfc503d6acd5f5abf91f503fa5ef/di#L790)
- Published comparisons. Fruit's wiki (last edited May 2020; Clang 10 / GCC 9; multi-file codebases built with `make` using N+1 jobs on a 32-thread machine; 90 % of classes with 10 dependencies) reports full compile times for 100 classes of 5.1–6.7 s for Fruit, 17–18 s for Boost.DI and 0.73–0.94 s for simple DI. For 1,000 classes it reports 48–64 s for Fruit and 580 s for Boost.DI with Clang (N/A with GCC) — [Fruit wiki: Benchmarks](https://github.com/google/fruit/wiki/benchmarks). Boost.DI's page (Clang 3.7, concrete types, 0 bindings) reports Boost.DI at 0.376 s for 64 types and 4.911 s for 1,024, against Fruit at 2.329 s and 69.6 s — [boost-ext/di doc/benchmarks.md](https://github.com/boost-ext/di/blob/20b6454c889f23c1e7c9eb5136cd7e3d6f6d718d/doc/benchmarks.md)

### Inferences
- In a single translation unit with interface bindings, Boost.DI scales best of the frameworks. Its own cost at N=100 is about 1.3–2.1 s on top of the 4.2–5.5 s that the generated classes cost anyway, and its marginal cost per component equals manual's. Fruit, Kangaru and dingo add about 12–23 s at N=100, about 2.7–4.6x Boost.DI's per-component cost. Hypodermic adds about 50–70 s.
- These single-TU results reverse the ranking on Fruit's wiki, where Fruit compiles about 3x faster than Boost.DI at 100 classes. The setups differ: Fruit's numbers come from parallel multi-file builds, which is Fruit's design point since each component is checked in its own TU; its classes have up to 10 dependencies; and the compilers are older. This experiment's one-component-per-TU variant (`multitu`) was not run, so which effect dominates is unverified.
- With Fruit, splitting bindings into many small component functions is not just style but necessary: one chained `createComponent()` expression with about 50 bindings exhausted 14 GB.
- qlibs/di's overload-set design suits small graphs only. Its cost appears to grow with the number of distinct dependency paths rather than with N. That is inferred from the provider-per-path design and the 2.75 s → 518 s jump, and was not profiled.
- At N≥50, Clang was faster than GCC or within about 5 % (dingo N=100 was 3 % slower; Hypodermic N=100 was 27 % faster) and always used less memory (Hypodermic N=100: 1.2 GB against 2.6 GB). At N≤25, GCC was often faster: Fruit, Kangaru and dingo by 5–20 %, and qlibs/di N=10 by more than 2x (2.75 s against 6.58 s).

### Gaps
- The container restarted during the original scaling run, so the data comes from two sessions. N=10 and N=25 are from the main run (600 s timeout, no memory limit) and were recovered from `measure.log`: medians only, no min/max, no binary sizes. N=50 and N=100 were measured afterwards, one compile at a time, under a 300 s timeout and an address-space cap of about 6 GB; no compile hit either cap. The qlibs/di N=25 Clang compile has no result.
- Not measured: multi-TU builds (the `multitu` phase for Fruit and manual is implemented but was not run), Boost.DI's module/exposed-injector splitting, incremental rebuilds, N>100, qlibs/di and flat Fruit at N≥50 (skipped after the N=25 blow-ups), and graphs with higher fan-in such as the 10 dependencies per class in Fruit's benchmark.
- Only one graph shape was used, and Hypodermic's N≥50 points are single runs.

## 5. Missing binding: when and how it is reported

### Takeaway
With the `IRepository` binding removed, Fruit, qlibs/di and the manual baseline fail at compile time with both compilers. Boost.DI fails at compile time with Clang, but with GCC 13.3 it only warns and then fails at link time unless `-Werror` is used, as its README's recommended flags do. Kangaru, dingo and Hypodermic compile silently and throw at run time. dingo's message is the most precise (type plus resolution path); Kangaru's doesn't name the missing type.

Among runtime containers, dingo > Hypodermic > Kangaru for message quality.
- Compile-time-checked frameworks (Fruit, Boost.DI with `-Werror` or Clang, qlibs/di) catch this class of error before tests run; runtime containers need a startup smoke test that resolves the root object.
- The Boost.DI GCC behaviour means a GCC build without `-Werror` can produce an object file and fail only at link time, far from the cause, so `-Werror=deprecated-declarations` (or full `-Werror`) is advisable with Boost.DI.

### Gaps
- Only one error class was tested (missing interface binding). Not tested: ambiguous bindings, lifetime/scope mismatches (e.g. reference to a unique object), cyclic dependencies, Boost.DI `BOOST_DI_CFG_DIAGNOSTICS_LEVEL=2`, Fruit's `FRUIT_DEEP_TEMPLATE_INSTANTIATION_STACKTRACES_FOR_ERRORS`.
- Error output length depends on defaults (GCC prints all errors; Clang stops after 20); not normalised.

## 6. Runtime cost of building the object graph

### Takeaway
Resolving the root from an existing container costs about the same as hand-wiring for Boost.DI and qlibs/di (26–36 ns). Kangaru costs about 40 ns, Fruit about 100 ns because of its factories, dingo about 270–330 ns, and Hypodermic about 600–660 ns. Building a fresh container plus the graph each time costs 53–58 ns by hand and in qlibs/di, 164–179 ns in Boost.DI with a per-injector scope, 0.55–0.58 µs in Kangaru, 1.5 µs in Fruit (0.66–0.74 µs from a NormalizedComponent), 1.1–1.2 µs in dingo and 7.6–7.8 µs in Hypodermic.

### Cited Findings
- Method: C++20, `-O2 -DNDEBUG`, 200,000 iterations x 7 repeats after a 10 % warm-up, pinned with `taskset -c 3`, sink = `asm volatile("" : "+m"(value) : : "memory")` on the resolved App; `graph` = construct container + register + resolve App + destroy; `resolve` = resolve App from a warmed container (creates App, Service and clock; shared objects reused); 1-minute load average 1.01 during the run — [experiments/common/bench.hpp](../../experiments/common/bench.hpp), [experiments/scripts/measure.py](../../experiments/scripts/measure.py), [experiments/results/results.json](../../experiments/results/results.json)
- Median ns/op, `graph` (GCC / Clang): manual 58.2 / 52.6; qlibs/di 55.6 / 58.9; Boost.DI core `singleton` 27.4 / 35.9 (shared objects are process-wide statics, so nothing shared is rebuilt); Boost.DI `extension::shared` 163.8 / 179.3; Kangaru 579.0 / 551.2; dingo 1,064.0 / 1,199.6; Fruit 1,529.2 / 1,516.6; Fruit from a pre-built `NormalizedComponent` 663.5 / 736.0; Hypodermic 7,845.0 / 7,619.2 — [experiments/results/summary.md](../../experiments/results/summary.md) (runtime table)
- Median ns/op, `resolve` (GCC / Clang): manual 26.6 / 26.5; qlibs/di 27.3 / 27.6; Boost.DI 29.0 / 35.7; Boost.DI `extension::shared` 32.6 / 41.0; Kangaru 39.8 / 40.8; Fruit 101.9 / 104.0; dingo 273.4 / 326.2; Hypodermic 656.5 / 598.4 — [experiments/results/summary.md](../../experiments/results/summary.md)
- Spread (min–max over 7 repeats) was mostly within ±5 %, but outliers occurred (e.g. dingo/Clang resolve 321.7–567.5 ns, Fruit/Clang graph_normalized 648.0–917.6 ns); an earlier exploratory run (20,000 x 3) gave Kangaru/Clang 844 ns graph / 68 ns resolve versus 551 / 41 ns in the final run, i.e. run-to-run differences up to ~50 % on this shared VM — [experiments/results/exploratory/bench_20k_x3.json](../../experiments/results/exploratory/bench_20k_x3.json), [experiments/results/results.json](../../experiments/results/results.json)
- Published comparison: Fruit's wiki reports per-request injection (create injector, inject all, destroy) for 100 classes of 2.5–3 µs (Fruit) vs 47–55 µs (Boost.DI) vs 0.44–0.83 µs (simple DI), and full startup injection times of 4.5–7.3 ms for all three — [Fruit wiki: Benchmarks](https://github.com/google/fruit/wiki/benchmarks); Boost.DI's page reports execution times equal to the baseline (0.002–0.004 s for 1024 iterations) and Fruit 18–190x slower (0.037–0.765 s) — [boost-ext/di doc/benchmarks.md](https://github.com/boost-ext/di/blob/20b6454c889f23c1e7c9eb5136cd7e3d6f6d718d/doc/benchmarks.md)

### Inferences
- The compile-time frameworks (Boost.DI, qlibs/di) have no measurable runtime overhead over hand-written wiring for resolving objects (Boost.DI/Clang +9 ns is within the noise seen here); Kangaru's overhead is small (+13–14 ns); the runtime containers pay hash-map/type-erasure costs per resolution (Fruit ~4x, dingo ~10–12x, Hypodermic ~22–25x the manual cost here).
- In absolute terms even Hypodermic's 7.8 µs to build a container is negligible for once-per-process startup; it matters only for per-request containers or hot-path resolution. For per-request use, Fruit's NormalizedComponent halves its cost, and Kangaru/Boost.DI with per-injector scopes are cheaper still.
- Our Boost.DI-vs-Fruit per-request result (Boost.DI cheaper) contradicts the direction in Fruit's wiki (Boost.DI 20x more expensive); the scenarios differ greatly (6 objects vs 100 classes with ~10 deps each, old compilers, and possibly Boost.DI's scope choice), so neither should be generalised.

### Gaps
- Single-threaded, tiny graph (5 objects per resolution); no measurement of large-graph runtime, thread-safety costs (Boost.DI's extension scope uses a mutex unless `BOOST_DI_NOT_THREAD_SAFE`), memory footprint per container, or cold-start (first-resolution) latency separately.
- Noise on a shared 4-vCPU VM is significant; results should be compared as ratios.

## 7. Practical friction: setup, builds, dependencies, CMake integration, header size

### Takeaway
qlibs/di (one ~1,000-line file, of which ~165 lines are code) and Boost.DI (one 3,355-line header) are the easiest to adopt: copy one header, no build step, no dependencies. dingo is header-only (51 headers) with a clean CMake interface target. Kangaru is header-only but its include tree is unusable without a generated `config.hpp`, made by CMake or by hand. Fruit must be built as a library, with a CMake setup that defaults to shared and Boost-enabled builds. Hypodermic needs Boost headers and has an outdated CMake setup.

### Inferences
- Adoption effort, lowest to highest: qlibs/di ≈ Boost.DI (single header) < dingo (header-only, CMake target) < Kangaru (header-only but needs a generated config header and per-type definitions) < Hypodermic (Boost dependency, dated build files) < Fruit (compiled library with non-default-friendly CMake options; but it is the only one designed for multi-TU component splitting).

- Maintenance signals differ sharply. dingo is under heavy active development (137 commits in the past 12 months, latest release 2026-04). ### Gaps
- Package-manager availability (vcpkg/Conan/distro packages) was not checked from inside this container, beyond files present in the repositories.
