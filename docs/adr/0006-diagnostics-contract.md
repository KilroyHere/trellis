# ADR-0006: The diagnostics contract

- **Status:** Accepted (owner, 2026-10-30)
- **Plan:** [§4](../plan.md#4-architecture-decisions) ADR-06; §3.2 NFR-07; §7.8; R3, R4
- **Spikes:** [S3 diagnostics rendering](../spikes/S3-diagnostics.md), whose recommendation the owner accepted with NFR-07 reworded. S1 and S2 add findings about deduced mode.
- **Amends:** plan §3.2 (NFR-07) and §7.8 (the example's literal; what each compiler prints; when the C++26 message is used; from T1.5's review, the provisional catalog rows E013 and E014; from T1.6, provisionally, the condition without the path, the note that names the path and one report per request and injector).

## Context

Three of the six frameworks the research measured compiled a missing binding without complaint, and Boost.DI under GCC only warns, then fails at link time (R3). Where errors exist, they are long and name little: for a missing `IRepository` binding, Fruit prints 22–30 lines with 4 errors, and qlibs/di 64–81 lines (S3 §3.3). Trellis wants every statically detectable mistake to be one hard error that names the type, the requested form, the path from the root and a fix (R4), within NFR-07's budget.

Spike S3 built a mock pipeline that follows plan §7.3 and §7.8, and compared nine renderings of E001, E005 and E012, at the root and three hops deep, on gcc-13, gcc-14, clang-18 and clang-20, in C++20 and C++26 modes: 240 compiles (S3 §2).

## Decision

1. **The contract:**
   - exactly one hard error per root cause;
   - the error names the error ID, the type, the requested form, the path from the root and a suggested fix;
   - the IDs (`TRL-E0xx`, `TRL-R0xx`, plan §7.8) are stable and documented in an error catalog;
   - output is golden-tested on every compiler;
   - no deprecation, undefined-function or link-time tricks.
2. **The mechanism, in every mode** (S3 §3.2, §4.1). `create<T>()` is `if constexpr (resolvable<...>) { creation code } else { explain pass; one static_assert; [[noreturn]] call; }`:
   - the creation code of a failing graph is never instantiated, so nothing cascades;
   - the `[[noreturn]]` call stands in for a return value, so it needs no value of `T`, which may be abstract or a reference, and it stops GCC's `-Wreturn-type`;
   - there is one `static_assert` per error kind, each in its own `if constexpr` branch with its own literal, written inline in `create`; a helper function or a macro adds 1–3 lines of "required from" or "in expansion of macro" on GCC (amended 2026-11-01, T1.6, provisional: every assertion is in one function template, `detail::raise<Error, Message, Scope>`, whose arguments name the error type, so that a report is raised once per request and injector however many roots reach it, and so that MSVC's instantiation note names the error type; see History);
   - the injector's type stays short, so GCC's instantiation banner stays one line (S3 §3.2; ADR-0010).

   Measured on all four compilers: 1 error, 0 warnings and 7–12 lines, under 1 KB at depth 3 and under 1.9 KB at depth 100 (S3 §3.1, §3.6). (Amended 2026-11-01, T1.6, after its review: S3's mock listed every constructor's parameters; with deduced constructors, the explain pass instantiates one function per deduced class on the failing path, from one line of the library, which Clang prints once and GCC folds into one line. A chain of 21 deduced classes is 14–17 lines on GCC 13, 26–29 on GCC 14 and 30–33 on Clang 18 and 20 in the layouts tested (an application header, four of them, the call over three lines); a chain of 240, 6.6–7.3 KB on GCC and 15.8 KB on Clang. A chain whose requests alternate between by value and by reference isn't folded and grows to the compilers' backtrace limit: 36–41 lines on Clang and 40–48 on GCC 14 at 20 classes, aggregates in the mix included, beyond NFR-07's 40 with four headers or a call over three lines; see History.)
3. **C++20 rendering** (S3 §4.2): `static_assert(error::E00x<T, request<R>, path<...>>::reported, "TRL-E00x: <summary>")`. Clang puts the condition, with the type, the request and the path, on the first error line. GCC puts the literal, which carries the ID, on the error line, and the condition in the attached note. So both parts carry information. (Amended 2026-11-01, T1.6, provisional: the condition names `error::E00x<T, request<R>>`, with the lifetime for E005, and no path; the path, `error::path<...>` with the 1-based parameter index, is in the instantiation note of the explain step that reports, `detail::explain_cause` (`owner_reporter` for an owner of an incomplete class): Clang's second note, after the error line, and GCC's first "required from" line, before it. A condition that named the path would be one error per root, as the Consequences below accepted; without it, one request that several roots fail on is one error, which the task's acceptance and T1.5's tests ask. See History.)
4. **C++26 rendering** (S3 §4.3): a P2741 message of four lines: the ID and the type; the requested form, the consumer and the parameter; the path; the fix. It is built at compile time into a `fixed_string` of exactly the right size, with one pass that counts characters and one that fills them in (S3 §3.5).
   - It is used when `__cpp_static_assert >= 202306L` in C++26 mode, **and also in C++20 and C++23 modes on GCC 14 or later and Clang 20 or later,** where it works as an extension. GCC 13 and Clang 18 reject it there, and Clang 19 wasn't tested, so it stays off for them.
   - `TRELLIS_HAS_STATIC_ASSERT_MESSAGE` in `config.hpp` gates it on compiler versions and `__cplusplus`, not on feature-test macros alone: clang-20 defines `__cpp_deleted_function` at `-std=c++20` and then warns when the feature is used. `#pragma GCC diagnostic ignored "-Wc++26-extensions"` surrounds the one assertion.
   - This puts the type on the first error line for gcc-14 and clang-20 in C++20 mode too.
5. **The explain pass** (S3 §3.5) runs only after a failure. It reads the memoized result of each parameter on the failing path, descends into the first failing one with the path extended and the 1-based parameter index, and classifies the deepest failure into an ID.
   - It makes depth + 1 instantiations and one read per parameter on the path, so it is O(depth × arity): 101 hops and 301 reads at N = 1,000 and depth 100.
   - It costs at most 5% over a build without it, which is within noise, and a failing build is 2.5–5 times cheaper than a passing one, because no creation code is instantiated.
   - It keeps the output's size bounded by the path, at about 8 bytes per hop, instead of by the number of bindings (S3 §3.6).
   - (Amended 2026-11-01, T1.6.) Through a declared class, the pass reads the memoized checks of its parameters in class templates, which print no note. Through a deduced class, whose parameters can't be listed, it finds the first failing parameter with one probe per parameter (the resolving placeholder at that position, discovery's probe at the others) and builds the class from placeholders in a function that is instantiated and never called, so that the selected operator, which knows the request, continues the pass. Details in [docs/internals/explain-pass.md](../internals/explain-pass.md).
6. **Long paths** are elided in the middle beyond about 8 hops, in the type and in the message, for example `path<App, A, B, elided<94>, X, Y, Z>` (S3 §4.5). This is Phase 4 work.
7. **`= delete("reason")`** (P2573) is fine for misuse whose reason is fixed text, such as copying an injector, in C++26 builds. It isn't the channel for wiring errors (S3 §4.4).
8. **NFR-07 is reworded by the owner:** "the first error line names the error ID; the same diagnostic names the type". S3 §4 found that the original wording ("the first error line names the type and the error ID") holds on Clang in every mode and on gcc-14 with the message, but not on gcc-13 in C++20 mode. There GCC prints only the literal, which carries the ID, on the error line, and the type follows in the attached note, the last line of a 7-line error. The 40-line budget holds with a wide margin: at most 12 lines with the recommended renderings, for every case, at depth 3 and at depth 100.
9. **Golden tests** use S3's normalization rules (S3 §3.7) plus `/` path separators, as `tools/golden.py` implements them since T0.10, which the owner approved. Line and byte budgets are measured on the default output that users see. Goldens compare the normalized text and are kept per compiler, because spellings differ (S3 §3.4).

### MSVC risk (S3 §3.8: high for the C++20 rendering, untested)

- MSVC prints `error C2338: static_assert failed: '<message>'` without the condition, so the error type, and with it the type and the path, would appear only in its "see reference to ... being compiled" notes.
- Mitigations to try in CI early in Phase 4: on MSVC, put the assertion inside a function or class template whose argument is the error type, so that the first instantiation note names it; or use P2741 once MSVC ships it (no shipped version is known). (Amended 2026-11-01, T1.6: the first is how every compiler reports now, through `detail::raise`; the platforms run will show what MSVC prints.)
- `__FUNCSIG__` names carry `struct ` and `class ` prefixes, so `type_name` needs one prefix-stripping pass on MSVC.
- `if constexpr` and `[[noreturn]]` are portable, so the one-error mechanism itself is low-risk.

## Alternatives

Renderings S3 measured (S3 §3.2, §4.4). Lines are for E001 three hops deep, on gcc-13 / gcc-14 / clang-18 / clang-20.

- **naive** (`static_assert(resolvable<...>)`, with the creation code still instantiated): 11 / 13 / 65 / 65 lines. Clang cascades into libstdc++'s `make_shared` with 3 errors, and nothing names the ID or the type.
- **leaf** (assert at the failing node inside the creation code): the compiler's backtrace is the path, so output grows by 2–6 lines per hop and passes 40 lines at about 5 hops on gcc-14 and Clang.
- **guard** (an `if constexpr` guard without the explain pass): names `resolvable<bindings<...>, App, unique>` instead of the cause, and prints the binding map, so bytes grow with the number of bindings: 63 KB on GCC and 36.9 KB on Clang at N = 1,000.
- **incomplete** (naming a member of an undefined `error::incomplete<Err>`): poor wording ("incomplete type ... used in nested name specifier") and a second error on clang-18.
- **A deleted `create` overload as the main channel:** on Clang the type lands in a note among "candidate template ignored" notes; P2573 reasons must be literals, so they can't name the type; and only Clang 19+ and GCC 15+ support them.
- **The deleted-overload rendering on GCC 13 only,** to keep NFR-07's original wording: a second code path to fix one compiler version that is going out of use.
- **ADR-06 as first drafted** (the message only where `__cpp_static_assert >= 202306L`): gcc-14 would show the type only in a note in C++20 mode.

## Consequences

- **T1.6 implements this** for E001–E005, E009, E010 and E012 in C++20 form. `TRELLIS_HAS_STATIC_ASSERT_MESSAGE` currently requires C++26 mode (T0.1), and T1.6 extends it with the compiler-version gate in item 4. (Amended 2026-11-01, T1.6: nothing uses the macro before the C++26 messages, so the gate moves to Phase 4 with them.) That answers T0.1's open question about messages before C++26. T1.6's acceptance text predates the rewording of NFR-07; under the reworded target, gcc-13 in C++20 mode meets it through the attached note.
- **Errors are reported once per failing `create<>` root,** not once per root cause across roots: two roots that fail on the same missing binding give two errors (S3 §5). (Amended 2026-11-01, T1.6, provisional: a report is raised once per injector and request across roots, and the error shows the path of the root that the compiler explains first; two roots that fail on different requests of one key, such as `sensor&` and `const sensor&`, are two errors. Within a root, the pass follows only the first failing parameter of each class, so a root reports one cause.)
- **Deduced mode limits the explain pass.** The pass needs each class's parameter list, which deduced mode can't enumerate (S2 §5). There it can name the consumer whose construction failed, but not the parameter; the deleted twin names the request in the compiler's note (S1 §3.1). S1 §5 asks that it still report E005 with the parameter index rather than a generic E002; T1.6 works out how. (Amended 2026-11-01, T1.6: the pass names the request and its parameter index in deduced mode too, item 5's amendment, at one instantiation note per deduced class on the failing path, which the compilers fold for a run of requests of one shape; see History.)
- **Where the error vocabulary lives (decided by the owner, 2026-10-31):** the compile-error vocabulary (`error::E00x`, `request`, `path`) lives in namespace `trellis::error`, outside `inline namespace v1`. GCC spells inline namespaces out (`trellis::v1::unique`) and Clang hides them, so this keeps names short and the same on both (S3 §3.2, §4.2). It is the one documented exception to the project's namespace rule. These types are versioned by error ID instead: an ID never changes meaning. Everything else stays in `inline namespace v1`, so two major versions can still coexist (plan §7.5).
- **A dependency cycle in deduced mode is an exception to "one error per root cause"** under ADR-0014: by default it ends in the compiler's own 2–6 errors, which the error catalog documents, and `options{.cycle_check = true}` gives exactly one TRL-E007.
- **A C++26 build costs a roughly fixed 0.3–0.4 s more** than a C++20 one at both depths, mostly from the language mode and its headers rather than from rendering the message (S3 §3.5).
- **Diagnostics come earlier:** the owner ordered Phase 4 (diagnostics) before Phase 3 (binding features) (plan §12.2), so the full catalog, the C++26 messages, path elision, golden tests on every compiler and the usability check follow Phase 2.
- **Not prototyped** (S3 §5): E002, E003, E006, E007 and cycles, and more than two lifetimes. GCC 15's SARIF output (`-fdiagnostics-add-output`) may suit golden tests better than text; it wasn't available.

  - The assertion fires inside the descent, so the compiler's instantiation notes trace the path, within the default backtrace limit of 10: 26–31 lines one hop down, up to 41 three hops down (Clang 18). The path in the error type, and NFR-07's 40 lines everywhere, are T1.6's.
  - TRL-E001 is raised for an abstract type without a binding, and for one bound to itself with `bind<I>` alone, with or without a constructor declaration (T1.2's follow-up: discovery's TRL-E002 for an abstract class with a declaration stays for discovery's own entry points).
  - TRL-E002 also covers a by-value request whose copy can't be made, with `E002<Key, request<R>>`.
- **2026-11-01, T1.5 review:** two mistakes that plan §7.8's catalog didn't cover get the next free numbers, as an ID never changes meaning: TRL-E013, an unbound concrete type requested in strict mode (an owning request that the implicit unique binding would otherwise serve), rather than widening TRL-E001, which keeps "no binding for an abstract type"; and TRL-E014, a `std::unique_ptr<I>` request that would delete the binding's implementation through `I`'s non-virtual destructor (plan §6.3, amended by ADR-0004), rather than stretching TRL-E005, which means "incompatible with the lifetime". Both are provisional and await the owner's confirmation (plan §7.8 amended; `[NEEDS CLARIFICATION]` in the progress log). The review also made `create<T>()` raise exactly one error where it raised two: for a by-value request of an abstract class, whose type a function can't return, `create<T>()` returns `void`; for a forward-declared type, which the check no longer asks `std::is_abstract` about; and for a parameter `std::unique_ptr<X>` of an incomplete `X`, whose destructor the failure pass no longer instantiates (docs/internals/resolution-and-storage.md).
- **2026-11-01, T1.6, provisional (for the owner):** the explain pass of item 5, with three changes to the decision; details and measurements in [docs/internals/explain-pass.md](../internals/explain-pass.md):
  - *Where the assertions live (item 2).* Every TRL `static_assert` is in `detail::raise<Error, Message, Scope>` (`diagnostics/errors.hpp`), which `create<T>()`'s explain pass, discovery, the request check, `make_injector` and the override check call. Its body is instantiated once per error type, message and scope (the injector for `create<T>()`'s reports), so a report is raised once however many roots, consumers or entry points reach it, and the note it adds names the error type, which is the MSVC mitigation above. It costs one note more than an inline assertion, 3 to 4 lines on the direct tests of discovery and the request check.
  - *The path (item 3).* It is in the instantiation note of the step that reports, `explain_cause<Path, Parameter, R, Injector>`, Clang's second note and GCC's first "required from" line, not in the condition (as of the review round below; T1.6's first version named it in the default template arguments of the operator above the error, which GCC's folding hides). The contract of item 1 holds: one error per root cause, and the diagnostic names the ID, the type, the request, the path and the fix. Putting the path in the condition would make one error per root, as the Consequences accepted, and contradict T1.6's acceptance ("exactly one static_assert fires per root cause") and T1.5's tests, which check one error for one request from two roots. The alternative, for the owner: the path in the condition and one error per root, which changes those tests' expectations (`create/e012_parameter_used_twice.cpp`, `create/e001_abstract_bound_to_itself.cpp`) and the order of E005's arguments that their regexes fix.
  - *Output size (item 2's measurements), T1.6's first version (superseded by the review round below).* Deduced classes make the pass instantiate functions, two per class on the failing path, and the output grows until the compilers' backtrace limit of ten contexts: Clang 18 and 20 then print 37 lines and GCC 14 39, within NFR-07's 40, when the user's call fits on one line; GCC 14 quotes every line of the call (two lines each), and each include level above `<trellis/trellis.hpp>` adds one. Three classes down, 24 and 25 lines (41 and 40 before). Through declared classes only, 15 and 16 lines at any depth.
  - Also: `make_injector` with `options{.eager = true}` runs the explain pass for the first singleton it can't build, before the injector exists, so eager mode's errors have one frame outside the pass too; and TRL-E009's error type and report exist, with the entry point T1.7's `override<K>` will call. T1.5's TRL-E013 and TRL-E014 (provisional IDs) go through the pass too. A deduced class that takes `std::unique_ptr` of an incomplete class by value can't be built even from placeholders, so the pass reports that parameter, from an unevaluated construction, and the incomplete class's TRL-E002 stays the only error.
- **2026-11-01, T1.6 review, provisional (for the owner):** two blocking findings, fixed in the explain pass; details in [docs/internals/explain-pass.md](../internals/explain-pass.md):
  - *Dependency cycles.* The first version followed a deduced cycle round and round, as the growing path made every step a new specialization: 20 errors and "too many errors emitted" on Clang, against ADR-0014 item 2's 2–6. The pass now stops at a class that is already on the path, or whose constructor requests one through a request whose node builds that class, before it reads that class's checks (a request that its own plan rejects first, such as `std::unique_ptr` of a singleton, never made the normal pass recurse and keeps its own error; T1.6 recheck): 3 errors on Clang and 1 on GCC by reference and in eager mode, 4 and 3 by value, all from the normal pass. Tests: `tests/compile_fail/explain/cycle_*.cpp`, at most six errors and no recursion limit.
  - *Output size.* NFR-07's 40 lines held only with the user's call on one line and `<trellis/trellis.hpp>` included directly. Each deduced class now costs one note, the operator that met its request, which builds the next class itself, from a pack that a lookahead finds one class ahead (six probes); the notes of a chain come from one line of `explain.hpp`, which Clang prints once and GCC folds, and the report goes through `explain_cause`, whose note names the path. A 21-class chain: 14–17 lines on GCC 13, 26–29 on GCC 14 and 30–33 on Clang 18 and 20 in the reviewer's layouts, which are tests now (`explain/deep_chain_*.cpp`, 40 lines). The path stays out of the condition: with it, two roots that fail on one request would be two errors, and T1.5's protected tests ask for one.
  - *Not solved: chains whose requests alternate between the two operator shapes,* `T` (by value, pointers, smart pointers) and `T&` (references). Each shape is its own conversion function template, so their constructions are on two lines, which the compilers fold only within a run; such a chain reaches the backtrace limit about six classes down: about 36 lines on GCC 14 plus one per level of include above `<trellis/trellis.hpp>` plus two per extra line of the call, and about 35 plus one per level of include on Clang (36–41 and 40–48 lines at 20 classes). A common function for both shapes would be a second note per class at a second location, which breaks every run. The owner decides between NFR-07's measurement conditions for these chains (the include chain and the user's own call excerpted are outside the library) and documenting `-ftemplate-backtrace-limit`.
