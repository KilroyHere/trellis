# Resolution and storage

How `injector::create<T>()` works (T1.5): the check that decides at compile time whether a request can be served, the creation code that serves it, and where the injector keeps the objects it owns. The explain pass, which reports why a request can't be served, is [explain-pass.md](explain-pass.md)'s (T1.6). Headers: [`include/trellis/static/resolve.hpp`](../../include/trellis/static/resolve.hpp) (resolution), [`include/trellis/static/storage.hpp`](../../include/trellis/static/storage.hpp) (slots and teardown) and [`include/trellis/static/injector.hpp`](../../include/trellis/static/injector.hpp) (the injector, `create<T>()`, eager mode). Decisions: [ADR-0014](../adr/0014-resolution-memoization-and-cycles.md) (memoization, depth per hop), [ADR-0006](../adr/0006-diagnostics-contract.md) (one error per root cause), [ADR-0005](../adr/0005-state-and-storage.md) (storage, teardown) and [ADR-0012](../adr/0012-threading-model.md) (slots, threads); the slot design is spike [S4](../spikes/S4-storage-threading.md)'s.

`create<R>()` is ADR-0006 item 2's structure, with nothing after the `if`, which MSVC would flag as unreachable (C4702):

```cpp
template <class R>
detail::create_result_t<R> create() {
  using root = detail::context<injector, unique_t, /* access, see "Eager mode" */>;
  if constexpr (root::template can_resolve<R>) {
    root ctx{*this};
    return ctx.template resolve<R>();   // the creation code
  } else {
    detail::explain_root_t<injector, R>::run();  // the explain pass (explain-pass.md): one report
    detail::unreachable();
  }
}
```

`create_result_t<R>` is `request_result_t<R>` (a reference, or the request without `const` and `&&`), unless no function can return that type: then `void` (see "One error, not two" below).

## The check: a plan and a node per request

**What it does.** `context<Injector, Lifetime>::can_resolve<R>` says whether request `R`, made by a consumer whose lifetime is `Lifetime`, can be served. It is a variable template:

```cpp
template <class R, class Node = typename plan<Injector, R>::node>
static constexpr bool can_resolve = node_v<Node>;
```

with two partial specializations, defined after the class, that evaluate the node of a deduced class themselves ([one variable template per hop](#one-variable-template-per-hop)).

- `plan<Injector, R>` works out, once per (injector, request), everything that doesn't recurse: the binding of R's key through the binding map, or the implicit unique binding of an unbound class (ADR-0004); the verdict of the request-form table (`request_check`, T1.4); strict mode; for a class the injector builds, whether it is complete and not abstract, whether discovery finds its constructor (`discoverable_v`, T1.3), from the declaration its binding makes with `.with_ctor<Args...>()` if any (`served_binding::binding_ctor`, T1.15) and whether a by-value request can be copied. Its `node` names what is left: `never_node<reason>` (false, with the reason the explain pass reports), `always_node` (an object a binding holds: true), or the construction of a class with every parameter resolved, `deduced_node<Impl, Ctx, Indices, Aggregate>` or `declared_node<Impl, Ctx, Aggregate, Args...>`.
- `node_v<Node>` evaluates a construction node directly. A deduced node is `__is_constructible(Impl, any_arg<Impl, Ctx>...)` (with braces in a requires-expression for an aggregate), whose overload resolution checks each placeholder's constraint `Ctx::can_resolve<T>`: the next hop. A declared node scans `Ctx::can_resolve<Args>...` in a braced list (no fold, plan §8.1 C3). `Ctx` is the class's own context: its binding's lifetime is its parameters' consumer lifetime.
- `select_node<Plan>()`, read through `decltype`, asks each question only once the ones before it are settled, in `if constexpr` branches, so a class with a missing binding is never probed.

**Why.** Memoization per (key, request form, consumer lifetime), and no path or depth in any type (plan §7.3, ADR-0014 item 1): `R` is the key and the form, the context carries the consumer lifetime, and each `(Injector, Lifetime, R)` triple is one variable template specialization, which compilers evaluate once. The consumer lifetime isn't consulted in Phase 1; it is in the key so that the captive rule (E006, Phase 2) fits.

The depth per hop decides the longest dependency chain that compiles at the compilers' default limits (NFR-09: 200 hops; GCC's `-ftemplate-depth` is 900, Clang's 1024). Everything in the plan finishes before the recursion starts, so a hop nests only `can_resolve<R>`, `node_v`, and the constraint check of the selected conversion operator: the lean shape of ADR-0014 item 3. (Since the Apple Clang fix below, a hop through a deduced class nests `can_resolve<R>` and the constraint check only; the measurements in this paragraph and the table are T1.5's.) The builtin matters: `TRELLIS_IS_CONSTRUCTIBLE` is `__is_constructible` where the compiler has it, and `std::is_constructible_v` costs one more level (it is a variable template), as does calling `deduced_constructible_v` (T1.3), which is the same check behind one more template. Measured in T1.5 on a chain of classes each taking the next, the smallest `-ftemplate-depth` that compiles 100 hops through `create<C0>()`, check and creation together:

| Node of a deduced class | gcc-13 | clang-18 | Deepest chain at the default limit, GCC / Clang |
|---|---|---|---|
| `node_v` with the builtin (T1.5) | 313 (3N + 13) | 415 (4N + 15) | 295 / 252, measured |
| `node_v` with `std::is_constructible_v` | 412 (4N + 12) | 514 (5N + 14) | about 222 / 202 |
| `node_v` through `deduced_constructible_v` | 511 (5N + 11) | 613 (6N + 13) | about 176 / 165 |

The deepest chain was measured by bisection on gcc-13 and gcc-14 (295 hops) and clang-18 and clang-20 (252), both for classes taken by value and for singletons taken by reference. At 100 hops the request form makes no difference: by value 313 / 415, `std::unique_ptr` 313 / 415, singletons by reference 315 / 415, singletons as `std::shared_ptr` 315 / 415. Declared constructors cost 2 levels per hop (214 / 217 by value, 216 / 223 for singletons by reference), as their node calls `can_resolve` directly. T1.14, on top of T1.6 and again on T1.7, measured the same deepest chains and the same depths at 100 hops, except that on GCC singletons by reference and as `std::shared_ptr` need 313 and declared constructors of singletons by reference 210, and that an eager injector's singletons need 317 / 419, 4 / 1 more than at T1.5, for T1.6's check in `make_injector` ([benchmarks](../benchmarks/v0.1.md#template-depth)). S2's lean stub reached 298 / 251 hops (ADR-0014 item 3). MSVC gets the builtin too, through `config.hpp` (it has no `__has_builtin`), and its own limits are in ADR-0014. T1.11 turned the measurement into a test, [the chain test](#the-chain-test).

### One variable template per hop

**What it does.** `can_resolve<R>` has a second template parameter, `Node`, whose default is R's node, and two partial specializations on it, for `deduced_node<Impl, Ctx, Indices, false>` and `deduced_node<Impl, Ctx, Indices, true>`. Their initializers are `node_v`'s two deduced expressions: `__is_constructible(Impl, any_arg<Impl, Ctx>...)`, and for an aggregate the requires-expression with braces. Any other node (a declared constructor, `always_node`, a `never_node`) still goes through `node_v<Node>`, which the explain pass and the tests use too, as they name a node rather than a request. The specializations are defined after the class: GCC 13 rejects a partial specialization of a member variable template inside it.

**Why.** Through `node_v`, the check of each hop instantiated two variable templates, `can_resolve<R>` and then `node_v<Node>`, and each instantiation costs a level of template depth and a share of the frontend's stack. Clang warns when its stack comes within 256 KiB of the 8 MiB it budgets (`-Wstack-exhausted`, `clang::DesiredStackSize`), and the project's warnings as errors make that an error. On Linux, that stopped the aggregate chain at 246 hops on Clang 20; on Apple Clang 21 it stopped the chain before 200 (platforms run 41327935786, NFR-09), for a reason of its own (below). A backtrace taken where Clang warns (gdb breaking in `clang::runWithSufficientStackSpaceSlow`, on Ubuntu's clang-20, with `-ftemplate-depth=4096` so that only the stack stops the chain) gives one hop's cost, frame by frame:

- 29,968 bytes for a class taken by value, and 32,432 for an aggregate. Each hop has two frames of about 7 KB. For the class taken by value, these are the `InitializationSequence` of `__is_constructible` and the `OverloadCandidateSet` that converts the placeholder to the parameter. For the aggregate, they are the `InitializationSequence` of `Impl{...}` and the one with which Clang initializes the field (`InitListChecker::CheckSubElementType`).
- The aggregate's extra 2,464 bytes are the requires-expression's substitution (about 1.8 KB, where the builtin's takes 0.6 KB) and the init-list checker's frames (1.8 KB, where the constructor overload's take 1.4 KB).
- The second variable template cost 3,328 bytes: `InstantiateVariableDefinition` (1,296), the reference that instantiates it, and the substitution of its initializer.

With the specializations, a hop of deduced classes costs 26,640 bytes by value and 29,104 for an aggregate on clang-20: an aggregate hop costs less than a by-value hop did before. Clang's check also nests 3 levels per hop instead of 4.

**Apple Clang 21 is another case.** With `-ftemplate-depth=4096` on copies of the generated chains, in the platforms workflow (runs 41338913950 and 41339845579), its by-value chain never reaches the stack's limit: it stops at the template depth, beyond 1,000 hops, so a by-value hop costs it less than 6 KB. Its aggregate chain stops at 181 hops, and at 195 with the specializations. What fills its stack is discovery's greedy check of each aggregate (`deduce`, discovery/deduced.hpp): `C{inert_arg}` finds no conversion to the field and elides braces into it, and so on through every aggregate below. Measured with the specializations and with any_arg's `not_self` written as a type-constraint of its real operators, which saves 0.6 KB per hop on Clang 20 and about 1 KB on Apple Clang (200 hops): without the greedy check for aggregates, the chain reaches 751 hops; with the aggregate node built with `__is_constructible`, 213; with parentheses in its requires-expression, 170.

Tried, and no better: building the aggregate with parentheses (`__is_constructible` on the aggregate, C++20's parenthesized aggregate initialization) costs 36,848 bytes per hop, with three 7 KB frames. A requires-expression with parameters in place of `std::declval` costs the same 32,432. A SFINAE partial specialization of `node_v`, with `decltype(Impl{...})` in its template argument, costs 33,744. The aggregate's two `InitializationSequence`s and its init-list frames are how Clang initializes an aggregate from braces, so an aggregate hop still costs about 2.5 KB more than a by-value hop.

**The trade-off.** `node_v` memoized a node's check once, however many requests shared the node. The specializations memoize it per (Injector, Lifetime, R), plan §7.3's key. So a deduced class requested in two forms, or by a ready context of an eager injector, has its constructor's overload resolution evaluated once more. Its placeholders still ask the node's checked context, whose checks are already memoized, so nothing below it is evaluated again.

## The creation code: three function bodies per hop

**What it does.** `context::resolve<R>()` serves the request, after the check passed, with one `if constexpr` branch per kind of binding and request form: a slot for a singleton (built on first use, by `build<Node, checked>::make_in`), `build<Node, Access>::value`, `fresh` or `share` for a new object (a prvalue, `new`, or a new `std::shared_ptr`), or the object a binding holds. `build`'s functions expand the placeholders themselves, `Impl(any_arg<Impl, Ctx>{ctx}...)`, with braces for an aggregate, so building a class is exactly what discovery checked (ADR-0003 item 5). A by-value request returns the prvalue, so a class that can't be copied or moved can be created.

The order in which a class's parameters are created is the compiler's order of evaluation of function arguments: unspecified for parentheses (GCC goes right to left, Clang left to right), left to right for braces. Dependencies always come before their consumer; teardown follows whatever order things were built in.

**Why.** GCC and Clang instantiate a function template's body where it is first used, so the creation code nests too, and its depth per hop counts against NFR-09 as the check's does (ADR-0014 item 3, §8.1 C7). Each hop nests exactly three bodies: `resolve`, the `build` function, and the placeholder's conversion operator, which calls the next `resolve`. Calling T1.3's `construct_deduced`, itself two functions, would add two levels.

A singleton is the place where the creation code could get deep: its slot's slow path and `std::make_shared`'s or `std::allocate_shared`'s internals are a dozen function templates between one `resolve` and the next. So the slot never sees the creation code: `resolve` takes the address of `build<Node, checked>::make_in<Cell>`, a plain `teardown_entry (*)(State& state, void* injector)` (`make_fn`, T1.14), and passes it to the slot's slow path, which calls it through the pointer. Taking the address instantiates `make_in` right in `resolve`. `make_in` hands the storage code a lambda that builds the object where it is told, `[&](std::byte* where) { ::new (where) Impl(any_arg<Impl, Ctx>{ctx}...); }`, through the slot's `make_with`. A lambda's body is instantiated with the function that contains it, so the placeholders' conversion operators are instantiated one level below `make_in`: a singleton hop also nests three bodies, `resolve`, `make_in` and the conversion operator, and the storage code that calls the lambda, however deep, stays off the chain. A `std::shared_ptr` request of a unique object goes the same way, through `build::share<Element>`. The indirect call happens once per singleton, and the storage code can inline the lambda, so building a singleton and storing it is one function: GCC inlines it, and Clang does where the constructor's parameters are few and cheap, as in the research scenario, and otherwise keeps the lambda as a function of its own, as in the generated graphs. Before T1.14 the slot got a build function, `place`, which a function of the storage called through a pointer: two functions per singleton (NFR-04, NFR-06).

**Tests:** `tests/unit/create_test.cpp`, `DeducedParametersAreResolvedInEveryForm`, `DeclaredConstructorsAndAggregatesAreBuiltAsDiscovered` and the request-form tests; the chain measurements above.

## The chain test

**What it does.** `tests/chain_depth/check_chain_depth.py` (T1.11; NFR-09, ADR-0014 item 3) generates a dependency chain of N hops: N + 1 classes, `C<N>` → … → `C0`, each taking the next as its constructor's parameter. It creates the root, an unbound class, with `create<C<N>>()`, so that N requests are resolved one inside the other, as spike S2 and T1.5 counted hops. It has ten shapes:

- one per request form the engine serves: by value (unbound classes), `std::unique_ptr` (interfaces bound to unique classes), a reference and a pointer (concrete singletons), and `std::shared_ptr` and `std::weak_ptr` (interfaces bound to singletons);
- declared constructors (a `trellis_ctor` alias, by value), aggregates (each holding the next by value), and an eager injector's singletons, taken by reference;
- a mix: the request forms in turn, with a `std::shared_ptr` of a unique class and the const forms of `singleton_inline` objects, and every class in turn deduced, declared by a `ctor_traits` specialization or an alias, or an aggregate.

CTest's `chain_depth.<shape>` compiles each shape's chain at the length NFR-09 asks of the compiler: 200 hops, or 150 on MSVC before 19.50. It uses the build's compiler and flags, with warnings as errors and without `-ftemplate-depth` or `/templateDepth`, so the compiler's default template depth decides. GCC and Clang compile with `-fsyntax-only`, and MSVC with `/c`, without debug information. `chain_depth.selftest` builds, links and runs every shape at 4 hops, or 37 for the mix, which then has every request form with every kind of class, and checks that the program built every object of the chain. `--deepest` finds the deepest chain per shape, up from 200 hops by doubling, then by bisection, and only a compiler limit ends the search. `--record` keeps the result in [`tests/chain_depth/deepest.json`](../../tests/chain_depth/deepest.json), which the tests print.

**Why.** `-fsyntax-only` instantiates everything a full compile does, the creation code's function templates included, and skips code generation, which dominates for a long chain of singletons: every function's symbol names the injector type, with all its bindings. A 294-hop chain of singletons takes gcc-13 6 s with `-fsyntax-only` and 66 s with `-c -g`, and both stop at 295 hops. That was checked on gcc-13 for the value and reference chains, and on clang-18 for the value chain. MSVC compiles in full, as S2's MSVC addendum did, because cl instantiates function bodies at the end of the translation unit (T1.13), and its syntax-only mode wasn't taken on trust. The bindings are listed from the root down, which matters only to an eager injector (below).

**Results** (T1.11, on T1.14). The deepest chain at the default limits with the debug presets, which `deepest.json` records under their names (the other presets have no record), in hops:

| Shape | gcc-13 | gcc-14 | clang-18 | clang-20 |
|---|---|---|---|---|
| by value, `std::unique_ptr`, reference, pointer, `std::shared_ptr`, `std::weak_ptr`, an eager injector | 294 | 294 | 251 | 251 |
| aggregates | 294 | 294 | 251 | 246 |
| declared constructors | 442 | 442 | 502 | 503 |
| the mix | 354 | 354 | 335 | 335 |

- **NFR-09 holds on GCC and Clang,** with 94 and 51 hops to spare in every request form, and 46 for aggregates on Clang 20. As T1.5 found, the request form makes no difference, and neither do aggregates, whose node's requires-expression nests as `__is_constructible` does, as far as the template depth goes.
- **Clang's stack.** Clang 20 compiles the aggregate chain up to 246 hops: one hop more, it emits `-Wstack-exhausted`, its warning that its stack is nearly exhausted, which the project's warnings as errors make an error; without them, the chain compiles up to the template depth limit, 251 hops. Clang budgets 8 MiB of stack, whatever `ulimit -s` allows above that, and checking an aggregate's braces takes more of it per hop than a constructor call. Apple Clang 21 stops the aggregate chain before 200 hops, mostly in discovery's greedy check ([one variable template per hop](#one-variable-template-per-hop) has the measurements). With the check's one variable template per hop, the aggregate and by-value chains stop at the stack on Clang, at 279 and 298 hops on Clang 20 and 284 and 305 on clang-18. The table above is T1.11's; the other shapes weren't measured again. With less than 8 MiB, Clang can crash first: with a 4 MiB stack, clang-20 crashes on the 200-hop value and aggregate chains, and clang-18 on the 251-hop aggregate chain, where gcc-13 compiles the 200-hop value chain. Linux's default stack is 8 MiB.
- **T1.5 measured 295 and 252 hops** on chains whose last class was an empty aggregate. The deepest instantiation is the discovery of the last class, at the bottom of the chain, and a last class with a constructor of its own costs 2 more levels on GCC and 3 on Clang: the value chain needs 3N + 16 levels on gcc-13 and 4N + 19 on clang-18 (316 and 419 at 100 hops), and 3N + 14 and 4N + 16 with an empty aggregate as its last class, which then reaches 295 and 252 hops too.
- **Declared constructors** nest 2 levels per hop, as at T1.5. The mix, where most classes are declared or aggregates, reaches 354 and 335 hops.
- **An eager injector** checks, then builds, its singletons in binding order (T1.6's check, then `build_eagerly`). With the bindings listed from the root down, as in the test, the first binding's check and creation nest the whole chain, and the chain stops where a lazy injector's does. Listed from the leaf up, every singleton finds its dependencies already checked and built, and the chain doesn't nest at all: 1,000 hops compile on gcc-13, and 300 on clang-18. That is ADR-0014's "creation code instantiated in binding order", which an eager injector does by itself. A lazy injector's chain nests whatever the order: its reference chain of 295 hops fails on gcc-13 in either order.
- **MSVC:** `platforms.yml` runs the test with the image's latest cl, at 200 hops, and with cl 19.44, at 150 ([ADR-0014](../adr/0014-resolution-memoization-and-cycles.md) records its result).

**Tests:** `tests/chain_depth/check_chain_depth.py` and `tests/chain_depth/CMakeLists.txt`: `ctest -R chain_depth`.

## Shared storage in one allocation

**What it does.** A `trellis::singleton` is held in a `std::shared_ptr` to the `Impl`, which `make_shared_object<Impl, Element>(build)` makes with one allocation for the object and its control block (`static/storage.hpp`, T1.14):

- **A class that shares from this,** with an unambiguous and accessible base `std::enable_shared_from_this<U>` (`shares_from_this<T>`, the condition under which `std::shared_ptr` sets it up, [util.smartptr.shared.const]/1), gets it from `std::allocate_shared<Impl>` with `construct_with<Impl>`, an allocator whose `construct(p, &build)` calls the build lambda. `allocate_shared(a, args...)` creates the object through `allocator_traits<A>::construct(a, p, args...)` ([util.smartptr.shared.create]/7.2), so the lambda travels as an argument and the allocator is empty.
- **Any other class** is built in a `shared_holder<sizeof(Impl), alignof(Impl)>` that `std::make_shared` creates: the object's bytes, and a pointer to the function that destroys it, set once the object is built. The `std::shared_ptr` aliases the object in the holder, so it shares the holder's control block, which destroys the object when the last owner lets go, as the object's own control block would.

The slot keeps a `std::shared_ptr<void>` to the object in raw bytes, built by `construct()` and destroyed by the teardown stack (`destroy_shared_pointer`, one function for every class). A request asks `share<Result>()`, which makes its `std::shared_ptr<E>` or `std::weak_ptr<E>` with the aliasing constructor: one more owner of the same control block.

**Why.** ADR-0005 item 2 prices the default at one allocation per singleton, as `std::make_shared` makes. `make_shared<Impl>` can't build the object the way Trellis must: it would use parentheses for an aggregate, and only a constructor call, not the placeholders' prvalue. `std::shared_ptr<Impl>(new Impl(...))` costs two allocations.

- **The allocator** gives one allocation, in-place construction with Trellis's rule, any class, copyable or not, and a plain `shared_ptr` that `enable_shared_from_this` and `weak_ptr` work with. It works on libstdc++ 13 and 14 and libc++ 18 (checked in T1.5); MS STL calls `allocator_traits` the same way (untested here). But it gives every class a control block type of its own, with five virtual functions, type information, and `allocator_traits<construct_with<...>>` for two types, which libstdc++ doesn't specialize as it does `std::allocator`'s. T1.5 used it for every singleton; T1.14 measured it at about as much compile time as the rest of a singleton's creation code: 200 classes compiled in 11.7 s against 8.8 s with `std::make_shared` on clang-18, and 1.3 s more on gcc-13.
- **The holder** gives one allocation too, with one control block type per size and alignment, shared by every class of that size, and `std::allocator<void>`'s `allocator_traits`, which libstdc++ specializes. An aliasing pointer doesn't set up `enable_shared_from_this`, which is why a class that shares from this keeps the allocator. Otherwise its behaviour is the allocator's: real shared ownership, `weak_ptr`s that expire with the last owner, the object destroyed by its own destructor whatever the pointer's type, its alignment kept, and `std::get_deleter` empty, as for any `make_shared` pointer. The holder adds the destroy function's pointer: 8 bytes, with the object's size rounded up to 8, or as many bytes as the alignment for a class aligned beyond 8 (`alignas(64)` and 128 bytes: a holder of 192). T1.5's allocator kept 16 bytes of state in each control block. The holder's bytes come first and are sized to end it at the pointer, so that the alignment pads nothing, which MSVC would report (C4324). Its default constructor is user-provided, so that `make_shared`'s value-initialization doesn't zero the bytes.
- **`std::shared_ptr<void>` in the slot,** rather than `std::shared_ptr<Impl>`, lets one function destroy every slot's pointer, and `share<Result>()` converts with the aliasing constructor, which is unconstrained, rather than with `shared_ptr`'s converting constructors, whose constraints cost more to compile per request.
- **`shares_from_this<T>`** deduces `U` from `T*` through `T`'s bases, which fails for two such bases, and converts `T*` to the base's pointer from `trellis::detail`, which fails for a base that isn't public: it holds exactly where `std::shared_ptr` enables `shared_from_this`, as libstdc++, libc++ and MS STL decide it.

A unique binding requested as `std::shared_ptr<T>` uses the same function, so it costs one allocation too.

## Slots: spike S4's state machine

**What it does.** `object_slot<Storage, threading::safe>` is S4's C+spin (ADR-0012 item 2): a one-byte atomic state, `empty`, `constructing` or `ready`, plus a waiters bit. The fast path, inlined into `resolve`, is an acquire load and a compare. The slow path (`build_once`, `TRELLIS_NOINLINE` and `TRELLIS_COLD`): compare-exchange `empty` to `constructing` and build; or find `ready` and return; or spin up to 128 times with `TRELLIS_CPU_RELAX()`, then set the waiters bit and block in `atomic::wait`. The building thread pushes the teardown entry, then publishes `ready` with an exchange, and calls `notify_all` only if the waiters bit was set. If the constructor throws, the slot is published `empty`, waiters wake, the exception reaches only this caller, and the next request retries (ADR-0012 item 6). Without `__cpp_lib_atomic_wait` (`TRELLIS_HAS_ATOMIC_WAIT` is 0), waiters block on a mutex and a condition variable per injector instead (item 3). `object_slot<Storage, threading::none>` is a plain `bool`.

The state and the slow path are `safe_slot_state` and `none_slot_state`, which aren't templates (T1.14). An `object_slot` derives from its state and adds the storage; `construct()`, which passes the slow path the `make_fn`, the injector and the teardown stack's `teardown_ref` (its entries and its counter, whatever its capacity); and `make_with`, through which the `make_fn` reaches the storage: a `static_cast` from the state, its base, to the slot. The retry's cleanup is a destructor, `publish_empty_unless_built`, which publishes `empty` while the exception passes on, rather than `catch (...)` and a rethrow.

Inline storage (`singleton_inline`) is the object's bytes, `alignas(T) std::array<std::byte, sizeof(T)>`, and the slot's state is its engaged flag, so a slot is `sizeof(T) + 1` rounded up to `alignof(T)`: 2, 16 and 65 bytes for 1, 8 and 64-byte objects, as S4 measured. A shared slot is 24 bytes.

Re-entry of a slot by the thread that is building it (TRL-R004) can only happen through `lazy`, which Phase 2 brings with the detection (ADR-0012 item 5); in Phase 1 a dependency cycle is a compile error (ADR-0014 item 2).

**Why.** ADR-0012 chose C+spin over `std::call_once` (slower warm, no R004, a TSan hang on retry) and over the mutex everywhere (88 bytes per injector, more include cost, slower with microsecond constructors).

The state machine needs only the state, the `make_fn` and the injector, so it needn't be a template on the object's type. Until T1.14 it was: each singleton had its own `construct`, `build_and_publish` and `publish`, each with the inlined `atomic::wait` and `notify_all`, about 0.5 KB of code per singleton on Clang. Now a program compiles it once. A destructor rather than `catch (...)` keeps the runtime's catch functions (`__cxa_begin_catch`, `__cxa_end_catch`, `__cxa_rethrow`) out of the binary, with the same semantics (NFR-06). `TRELLIS_COLD` makes GCC and Clang optimize the slow path for size and keep it apart from the hot code.

**Tests:** `tests/unit/threading_test.cpp`: 8 threads request a 16-node graph with nested dependencies in different orders, 30 rounds, with exactly one construction per node and one address per node across threads; teardown after such a race destroys each node before the nodes it depends on, whichever threads built them (30 rounds); threads that arrive during a 20 ms construction wait for it; a constructor that fails 3 times while 8 threads wait gives exactly 3 exceptions and one object. The tsan preset runs them under ThreadSanitizer, and `trellis_wait_fallback_tests` runs them again with `TRELLIS_HAS_ATOMIC_WAIT=0` (test names `wait_fallback.*`). `tests/unit/create_test.cpp` checks the slot sizes and the retry on one thread; `tests/unit/no_exceptions_create_test.cpp` builds the slots without `try` and `catch`.

## The teardown stack and the slot store

**What it does.** `teardown_stack<Capacity, ThreadSafe>` is a `std::array` of `{destroy function, object}` pairs and a counter (an atomic with relaxed `fetch_add` under `threading::safe`), with one entry per slot. A slot pushes after its object's constructor succeeds and before it publishes `ready` (ADR-0005 item 4, rule 1), so a dependency's entry lands below its dependents', even across threads, and a failed construction pushes nothing. The injector declares the stack after the slots, so the stack's destructor destroys the objects, in reverse order, before the slots' storage goes (rule 2), and after the bindings' values, which singletons may refer to, are still alive. A slot holds nothing else to destroy, an object or a `std::shared_ptr` in raw bytes, so the slots are trivially destructible and the injector's destructor has no code per slot (T1.14; with a `std::shared_ptr<Impl>` member, the injector's destructor destroyed each slot's pointer again: 11 KB of code at 100 singletons).

The slots are `slot_store<Mode, Indices, Bindings...>`, one base `slot_holder<J, B, Mode>` per binding position J, like T1.4's binding store: the binding map gives the position and the binding type together, so a slot is a `static_cast` away. A binding the injector doesn't own (unique, external, value) gets an empty holder with no base. The empty holders of one store are distinct types, so GCC and Clang lay all of them out at offset 0, as the Itanium ABI does for distinct empty bases, and they take no space.

**Why.** Plan §7.5 sketched the slots as a `std::tuple<slot<B>...>` (amended by ADR-0005, 2026-11-01, T1.5): `std::tuple`'s recursive implementation nests a class per element, which T1.4 avoided for the bindings for the same reason, and indexed bases need no lookup at all. MSVC gives each empty base after the first a byte unless the class is declared `__declspec(empty_bases)`, so `slot_store` and T1.4's `binding_store` carry `TRELLIS_EMPTY_BASES`, and T1.4's stored bindings spell their attribute `TRELLIS_NO_UNIQUE_ADDRESS`, `[[msvc::no_unique_address]]` on MSVC (`config.hpp`; untested here; `create_test.cpp` checks that a store of unowned bindings and a module of empty bindings are 1 byte).

**Tests:** `tests/unit/create_test.cpp`: `TeardownReversesTheOrderOfConstruction` (shared and inline singletons with nested dependencies and a unique member, checked against the construction order recorded), `AThrowingConstructorLeavesTheSlotRetryable` (S4's `E(F, G)` case: `F` stays built, the unique object built for the failed attempt is destroyed, and teardown is `E, G, F, H`), `SingletonsArePerInjector`, `UnrequestedSingletonsAreNeverBuilt`, and static asserts on the stack's size (1,608 bytes for 100 entries), on a store of unowned bindings being empty, and on slots being trivially destructible.

## Eager mode

**What it does.** With `options{.eager = true}`, the injector's constructor requests every binding it owns by reference, in binding order, through checked contexts: each request builds its dependencies first, so the singletons are built in dependency order, and the teardown stack records the order they were built in. If a constructor throws, the exception leaves the injector's constructor, and the members' destructors tear down what was built, in reverse order: `make_injector`'s strong guarantee (plan §7.5). Afterwards `create<T>()` uses contexts with `slot_access::ready`, whose `resolve` reads a singleton's object without testing its slot and without instantiating its build function: plan §7.6's "every access is a plain read" (ADR-0012 item 7).

**Why.** The access is a template parameter of the context, `context<Injector, Lifetime, Access>`, which changes only `resolve`: `can_resolve<R>` evaluates the same node for every access, and the nodes name checked contexts, so the check is memoized once. (A ready context's `can_resolve<R>` evaluates a deduced class's node itself, [one variable template per hop](#one-variable-template-per-hop), but its placeholders ask the checked contexts, whose checks are done.) An eager injector instantiates the singletons' creation code once, in its constructor.

A singleton that can't be built is found by `make_injector`, before the injector exists: it runs the explain pass for the first such singleton, in binding order (T1.6, [explain-pass.md](explain-pass.md)), so the constructor's `build_eagerly` only ever builds.

**Tests:** `tests/unit/create_test.cpp`, `EagerModeBuildsEverySingletonInMakeInjector` and `EagerModeGivesTheStrongGuarantee` (S4's case: node 4 throws, nodes 3, 2, 1 and 0 are destroyed in that order); `tests/compile_fail/create/eager_e012.cpp` (a singleton that can't be built fails in `make_injector`, once) and `tests/compile_fail/explain/eager_singleton_eight_down.cpp`.

## The failure pass, replaced by the explain pass (T1.6)

T1.5's failure pass, `explain<Injector, R>()`, followed every failing request with three functions per class and asserted where it found a cause, so the compiler's notes traced the path: 26–31 lines one class down, up to 41 on Clang three classes down. T1.6 replaced it with the explain pass, which follows only the first failing request, steps through declared classes without a function of its own, and reports through `detail::raise`, which is unique to the request rather than to the path: [explain-pass.md](explain-pass.md). What T1.5 decided for each of the plan's reasons stands, as `own_report`:

| The plan's reason | Reported |
|---|---|
| keys repeat | nothing: `make_injector` has reported TRL-E003 |
| the table rejects the request | the request check's report (T1.4): TRL-E005 or TRL-E012 |
| an abstract type without a binding | TRL-E001 |
| an owning request of a type without a binding, under `options{.strict = true}` | TRL-E013 (provisional ID); the table's verdict comes first, so a reference to an unbound type stays TRL-E012 |
| an abstract type bound to itself (`bind<I>` alone) | TRL-E001, before discovery is asked, with or without a declaration |
| `std::unique_ptr<Key>` of a derived implementation, `Key`'s destructor not virtual | TRL-E014 (provisional ID) |
| the class's constructor can't be found, or the class is only declared | discovery's own report: TRL-E002, TRL-E004 or TRL-E010 |
| a by-value request whose copy can't be made | TRL-E002 |
| the class's node fails | its first failing parameter, explained in turn |
| the class is on the path already, or its constructor requests a class that is: a dependency cycle | nothing more: the normal pass has reported the cycle with the compiler's errors (ADR-0014 item 2) |

**Tests:** the tests in `tests/compile_fail/create/` and `tests/compile_fail/explain/`, each of which allows exactly one error line; `tests/unit/resolve_forms_test.cpp`, "FailurePassAgrees": for each of S1's 32 deducible forms, building `consumer<P>` from `explain_arg` asks exactly the request S1 recorded, which `any_arg` resolves (`tests/unit/deduced_test.cpp`), and the owner check finds no owner of an incomplete class, so the placeholders can't drift from the probe's shapes.

## One error, not two

T1.5's review found three requests that gave a second error beside the failure pass's one (now the explain pass's), and T1.6's review a fourth; each is now one error, or none.

- **A by-value request of an abstract class,** such as `create<IShape>()`, unbound, bound to an implementation or bound to itself. A function can't be declared to return an abstract class, so naming `request_result_t<R>` as `create<R>()`'s return type was an error of its own. `create_result_t<R>` is `void` where the result isn't `returnable` (an abstract or incomplete class, an array, a function type, or a `std::unique_ptr` to an incomplete class, which a call can't return as its temporary can't be destroyed); no such request can be served, so the valid ones keep their type. `returnable` asks `std::is_abstract_v` only after `complete_class`, in a concept's conjunction, which checks its second constraint only when the first holds. Tests: `e001_root_abstract_by_value.cpp`, `e002_root_abstract_bound_by_value.cpp` and `e001_root_abstract_bound_to_itself_by_value.cpp`.
- **A type that is only declared,** such as the pointee of a `database*` parameter. The request check asked `std::is_abstract_v<Key>` of every unbound key, which is an error for an incomplete one, and the cascade reached the plan's `if constexpr` chain. `complete_abstract<Key>` (`static/validate.hpp`) checks completeness first, the same way, so such a request goes on to the table (TRL-E012 for a pointer or reference) or to discovery (its one TRL-E002, "it is incomplete here"). Test: `e012_incomplete_by_pointer.cpp`.
- **A parameter `std::unique_ptr<X>` of an incomplete `X`.** Building the consumer from placeholders instantiates the parameter's destructor, and `std::default_delete<X>` asserts that `X` is complete: a second error after discovery's. So the explain pass looks for such a parameter first, with `owner_probe`, a placeholder with the probe's shapes whose by-value operator refuses an owner of an incomplete class (`owns_incomplete`), and reports it rather than the first failing parameter: the class is built only unevaluated, with an `owner_reporter` at that parameter, whose operator's constraint raises the owner's report, discovery's TRL-E002 for `X`, so no destructor is instantiated ([explain-pass.md](explain-pass.md); T1.6 replaced T1.5's `owner_arg`, which did the same in the failure pass). The class's other failing parameters are reported once `X` is complete. Test: `e002_incomplete_unique_ptr_parameter.cpp`, with the request at the root, as a parameter and as an aggregate's member.
- **A binding of an object whose type is only declared** (`.to_ptr(p)`, `.to_ref(x)`; T1.6's review, T1.7's finding). The plan asked `std::is_constructible_v<Key, const Impl&>` beside `form == value` in one condition, which instantiates both operands, so every request of the binding was an error of its own. Each question now has its own `if constexpr` branch: a reference or pointer request is served, and only a by-value request asks whether the key can be copied, after `complete_class<Key>`: TRL-E002 for an incomplete key (`tests/unit/create_test.cpp`, `IncompleteTypesBoundByPointerOrReference`; `tests/compile_fail/create/e002_copy_of_incomplete_object.cpp`).

## Choices for types without a constructor to discover

- **Unbound non-class types,** such as `int`, are implicitly unique for the request-form table, as T1.4 treats them, and have no constructor to discover: a by-value request is discovery's TRL-E002, "deduction needs a class type; bind the type to a value", and a reference is TRL-E012. They are never value-initialized silently, which would inject a 0 into a constructor that expects configuration ([NEEDS CLARIFICATION] in T1.5's progress entry).
- **An aggregate's fields are requests,** base classes first (ADR-0003 item 5). A class without a constructor of its own that derives from a base is an aggregate, so its base is a field and is requested by value; a class that should be built with no arguments needs a user-declared constructor, even `X() = default;`.
- **Deleting through a base class** (T1.5's review; plan §6.3 amended by ADR-0004). `std::unique_ptr<Key>` of a binding whose implementation derives from `Key` is TRL-E014 when `Key`'s destructor isn't virtual (`deletes_through_base`), as `std::default_delete<Key>` would delete the implementation through `Key`. It is asked only for a derived implementation, so a key that is its own implementation needn't be complete. A `std::shared_ptr<Key>` is safe, as its control block deletes the class it was made for, and so are slots and by-value requests (`create_test.cpp`, `NonVirtualBaseFormsDestroyTheDerivedClass`; `e014_unique_ptr_without_virtual_destructor.cpp`).
